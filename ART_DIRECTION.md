# ART_DIRECTION.md — Inclusive Interface

## 1. Purpose

This is the **authoritative visual direction** for Inclusive Interface.

It prevents the game from drifting into cyberpunk, sci-fi dashboards, neon HUDs, or generic AI-game aesthetics.

> **The game must look like a human, atmospheric, retro pixel-art narrative RPG — not a futuristic accessibility simulator.**

---

## 2. One-Sentence Art Direction

> **A nostalgic pixel-art narrative RPG / visual-novel hybrid set in an ordinary fictional city, with expressive characters, atmospheric environments, restrained UI, and occasional cinematic glitch transitions.**

Visual formula:

```text
RETRO HANDHELD RPG
        +
PIXEL-ART ADVENTURE
        +
VISUAL NOVEL DIALOGUE
        +
CINEMATIC STORYTELLING
```

Not:

```text
CYBERPUNK
        +
SCI-FI HUD
        +
NEON DASHBOARD
```

---

## 3. Primary Visual Reference

The team's provided inspiration should guide:

- composition
- pixel-art density
- character presentation
- dialogue presentation
- environment design
- nostalgic atmosphere

Do not directly copy characters, sprites, logos, UI, branding, or proprietary artwork.

The game needs its own original visual identity.

---

## 4. Intended Feeling

The player should feel:

```text
nostalgic
curious
human
slightly mysterious
warm
immersive
playful
thoughtful
cinematic
```

The city should feel like a place where ordinary people live.

It should NOT feel like:

```text
a laboratory
a spaceship
a cyberpunk terminal
a futuristic operating system
a developer dashboard
```

---

## 5. Visual Pillars

Everything should follow:

1. **Human** — believable people and lived-in places.
2. **Retro** — intentional pixel-art language.
3. **Atmospheric** — lighting, interiors, weather, and backgrounds create mood.
4. **Narrative** — composition supports storytelling.
5. **Restrained** — UI stays out of the way.
6. **Accessible** — the actual game remains readable and usable.

---

## 6. Explicitly Rejected Visual Direction

Do NOT use:

```text
❌ Cyberpunk city
❌ Neon cyan/magenta everywhere
❌ Futuristic holographic UI
❌ Sci-fi control panels
❌ Giant permanent HUD
❌ Energy bars during normal exploration
❌ Credits/currency HUD without gameplay purpose
❌ Fake console frame around the whole game
❌ PSP/DS controller overlay as default presentation
❌ "ACCESS ARCHITECT" branding
❌ Generic AI-generated game interface
❌ Glowing rectangles everywhere
❌ Excessive scanlines
❌ Random technical labels
❌ Decorative technical jargon
```

Do not add visual elements merely because they "look game-like."

---

## 7. World Design

The world is an ordinary fictional city.

Possible locations:

```text
residential street
small park
cafe
bus stop
hospital
library
design office
small shops
community center
```

Use believable everyday elements:

```text
roads
sidewalks
buildings
windows
doors
streetlights
trees
benches
signboards
cars
buses
people
```

---

## 8. City Scale

The MVP does NOT need a huge open world.

Prefer:

```text
small
dense
walkable
recognizable
```

over:

```text
huge
empty
procedurally generated
```

The player should understand the city layout quickly.

---

## 9. City Composition

A normal scene should communicate:

```text
sky/background
buildings
trees
street
shops/public locations
NPCs
player
```

The city should look like a place, not a technical diagram.

---

## 10. Camera

Exploration should use a 2D RPG camera.

Preferred:

```text
top-down
three-quarter top-down
side/top hybrid
```

The player should clearly see:

```text
character
environment
NPCs
interactive objects
```

Avoid an excessively zoomed-out camera.

---

## 11. Character Scale

Characters must be recognizable.

Give sprites:

- distinct silhouettes
- hair
- clothing
- body proportions
- facial direction
- personality
- walking/idle states

Avoid characters that look like colored blocks.

---

## 12. Character Design

Important characters should have:

```text
distinct hairstyle
distinct clothing
distinct silhouette
distinct palette
idle animation
walking animation
talking pose/expression
```

Do not create generic clones with different shirt colors.

Accessibility-related traits must not become the character's entire identity.

---

## 13. Rahul, Fatima, Mira

Rahul, Fatima, and Mira should all look like ordinary people with individual personalities.

Their accessibility needs should be communicated primarily through:

```text
dialogue
context
interaction
gameplay
```

not caricature or exaggerated visual effects.

The design principle is:

> **Character first, accessibility need second.**

---

## 14. Character Portraits

Important dialogue may transition into a visual-novel-style composition:

```text
GAME WORLD
    ↓
CHARACTER PORTRAIT
    ↓
DIALOGUE BOX
```

Portraits should be pixel-art or pixel-compatible.

---

## 15. Dialogue Box

Dialogue boxes should be:

```text
simple
retro
readable
slightly decorative
```

They should resemble a classic RPG/visual novel window.

They should NOT resemble:

```text
cyberpunk command panels
futuristic HUD windows
holographic dashboards
```

---

## 16. Dialogue Typography

Use a readable retro/pixel-compatible font where appropriate.

Priorities:

```text
readability
character
hierarchy
```

Do not use tiny or excessively distorted text.

---

## 17. Exploration UI

Keep exploration UI minimal.

Recommended:

```text
small score indicator
small objective indicator when needed
interaction prompt
```

Example:

```text
SCORE 1250

             GAME WORLD

             [E] TALK
```

Do NOT add unnecessary:

```text
energy
credits
battery
technical diagnostics
```

unless they have a real gameplay purpose.

---

## 18. No Permanent Console Frame

The game must NOT be presented inside a giant fake:

```text
PSP
Nintendo DS
arcade machine
futuristic portable device
```

frame.

Retro handheld games are an aesthetic reference only.

The browser displays the game itself.

---

## 19. Color Direction

Use a restrained palette.

Good families include:

```text
warm cream
muted brown
soft green
dusty blue
warm gray
muted red
soft yellow
```

Night scenes may use:

```text
deep blue
purple-gray
muted teal
```

Bright colors are accents, not the entire palette.

---

## 20. Neon Usage

Neon is allowed only as a small accent when it has a reason.

Good:

```text
small selection highlight
brief glitch artifact
important system message
```

Bad:

```text
neon border around every panel
neon city
neon NPCs
neon roads
neon HUD
```

---

## 21. Lighting

Use lighting to create atmosphere.

Morning:

```text
soft sunlight
blue sky
warm buildings
```

Evening:

```text
orange light
long shadows
warm windows
```

Night:

```text
deep blue sky
street lamps
lit windows
quiet atmosphere
```

Do not use constant artificial neon lighting.

---

## 22. Developer Room

The developer's room should feel personal and believable.

Include:

```text
desk
laptop
chair
bed
books
clothes
window
small objects
```

The laptop establishes the protagonist's identity.

The room should NOT look like a sci-fi command center.

---

## 23. Appointment Website

The appointment website is intentionally inaccessible.

It may contain:

```text
tiny text
poor contrast
unclear hierarchy
small controls
confusing labels
bad CAPTCHA
```

But it should still look like a believable ordinary website.

It should NOT look like a cyberpunk terminal.

---

## 24. Appointment Transition

When the player opens the appointment service:

```text
GAME WORLD
      ↓
SUBTLE GLITCH
      ↓
FULL-SCREEN WEBSITE SIMULATION
```

The player should feel that they entered a digital interface.

---

## 25. Realization Visuals

This is intentionally minimal:

```text
BLACK
```

Then:

> YOU DIDN'T FAIL.

Pause.

Then:

> BUT THE INTERFACE DID.

No HUD.

No score.

No character sprites.

No decorative dashboard.

Only typography and controlled glitch.

---

## 26. Glitch Language

Glitch is a narrative device.

Use it for:

```text
opening
appointment transition
realization
major level transitions
ending
```

Do NOT use it continuously.

Preferred glitch language:

```text
old digital signal
CRT distortion
brief pixel displacement
text flicker
small screen tearing
frame corruption
```

Avoid giant sci-fi holograms and constant RGB effects.

---

## 27. Challenge UI

Challenge screens should still feel like part of the RPG.

Use:

```text
character
scenario
question
options
```

with a restrained retro interface.

Example:

```text
┌──────────────────────────────────────┐
│ RAHUL                                │
│ VISUAL ACCESSIBILITY                 │
├──────────────────────────────────────┤
│                                      │
│ Rahul is trying to book an           │
│ appointment.                         │
│                                      │
│ What should the designer change?     │
│                                      │
│ > Add clear labels                   │
│   Add more colors                    │
│   Add animation                      │
│   Make the buttons smaller           │
│                                      │
└──────────────────────────────────────┘
```

---

## 28. Challenge UI Must Not Become a Dashboard

Avoid:

```text
large score panels
energy meters
credit counters
technical diagnostics
multiple glowing status bars
```

The player should focus on the design decision.

---

## 29. Score

Use small temporary feedback:

```text
+125
```

after a correct decision.

Do not keep a giant score display in the center of the screen.

---

## 30. Progress

Use simple RPG-style indicators.

Example:

```text
RAHUL

EASY
● ● ○

MEDIUM
🔒 🔒 🔒
```

Progress should inform without becoming a dashboard.

---

## 31. Difficulty

Use:

```text
EASY
MEDIUM
HARD
```

Difficulty describes design complexity, not character strength.

Avoid:

```text
LEVEL 9000
COMBAT POWER
ENERGY
```

---

## 32. NPC Interaction

Near an NPC:

```text
[E] TALK
```

should appear subtly.

Do not make the prompt dominate the scene.

---

## 33. NPC Placement

Place characters naturally:

```text
Rahul near a public service
Fatima near a bus stop
Mira near a shop
Grandma at home
```

Their locations should support the story.

Do NOT place all characters in a row like a character-selection screen.

---

## 34. Exploration Animation

Use subtle:

```text
walking
idle movement
NPC movement
environment movement
```

The city should feel alive without requiring complex physics.

---

## 35. Environment Depth

Where practical, use:

```text
foreground
playable layer
background
```

to create depth while maintaining pixel-art style.

---

## 36. Background Detail

Include enough environmental detail to feel lived-in:

```text
windows
signboards
trees
lamps
benches
cars
posters
shops
doors
```

Do not fill the environment with glowing technical text.

---

## 37. UI Borders

Use restrained borders inspired by:

```text
retro handheld interfaces
pixel-art frames
classic RPG windows
```

Good:

```text
┌─────────────────────┐
│ Dialogue            │
└─────────────────────┘
```

Avoid futuristic technical panels.

---

## 38. Icons

Use simple pixel-art icons:

```text
speech bubble
arrow
interaction symbol
check
cross
map marker
```

Avoid holographic/futuristic icons unless specifically justified.

---

## 39. Menus

Menus should be:

```text
simple
retro
clear
quiet
```

Possible:

```text
RESUME
CHARACTERS
PROGRESS
SETTINGS
QUIT
```

Do not add statistics just to make the interface look complex.

---

## 40. Settings

At minimum:

```text
Sound
Music
Text Speed
Reduced Motion
```

Additional accessibility settings can be added later.

---

## 41. Actual Game Accessibility

The game itself must practice what it teaches.

Where practical:

```text
readable text
keyboard navigation
visible focus
captions
text equivalents
no color-only critical information
reduced motion
pause support
```

The intentionally inaccessible appointment simulation is the controlled exception.

---

## 42. Pixel-Art Technical Direction

Prefer:

```text
low-resolution source assets
nearest-neighbor scaling
integer scaling where practical
consistent pixel density
consistent sprite proportions
```

Avoid mixing incompatible visual styles without a deliberate narrative reason.

---

## 43. Pixel Density Consistency

Do not combine randomly:

```text
tiny 8-bit sprite
high-detail sprite
smooth vector character
photorealistic background
```

All major assets should feel like they belong to the same game.

---

## 44. Animation Style

Keep animation economical.

Examples:

```text
2–6 frame walk cycle
2–4 frame idle
portrait expression changes
simple UI transitions
```

Polish a small set of animations instead of creating many unfinished ones.

---

## 45. Visual Novel Mode

Important conversations can use:

```text
character portrait
+
background
+
dialogue box
```

This provides a stronger narrative feel without abandoning the RPG world.

---

## 46. Scene Transitions

Normal:

```text
fade
```

Important narrative transition:

```text
fade + subtle glitch
```

Major realization:

```text
black screen + glitch + typography
```

The visual language should have meaning.

---

## 47. Interface Transformation

When a player makes a correct design decision:

```text
OLD UI
   ↓
brief transition
   ↓
NEW UI
```

Possible effects:

```text
pixel dissolve
small glitch
fade
component replacement
```

Do not use excessive particles or explosions.

---

## 48. Audio Direction

Audio should feel like a retro narrative game.

Possible:

```text
soft chiptune
lo-fi RPG ambience
subtle city ambience
dialogue blips
interaction sounds
glitch sound
```

Avoid making the entire soundtrack cyberpunk synthwave.

---

## 49. Asset Rules

Use:

```text
original assets
properly licensed assets
assets generated for this project
```

Do not directly use copyrighted:

```text
Pokemon sprites
Persona sprites
Nintendo assets
Roblox assets
PSP UI assets
other proprietary game assets
```

References establish aesthetic direction only.

---

## 50. Anti-Cyberpunk Checklist

Before committing visual work:

```text
[ ] No giant futuristic HUD
[ ] No unnecessary energy bar
[ ] No unnecessary credits counter
[ ] No permanent console frame
[ ] No neon-heavy city
[ ] No holographic panels
[ ] No sci-fi terminology
[ ] No excessive glow
[ ] No constant glitch
[ ] No generic cyberpunk dashboard
```

---

## 51. Pixel-RPG Checklist

Every major scene should have:

```text
[ ] readable pixel-art characters
[ ] believable environment
[ ] restrained UI
[ ] clear interaction
[ ] atmospheric background
[ ] consistent pixel scale
[ ] narrative purpose
```

---

## 52. City Checklist

The city should have:

```text
[ ] homes
[ ] streets
[ ] public locations
[ ] believable buildings
[ ] environmental props
[ ] natural NPC placement
[ ] walkable space
[ ] visual landmarks
[ ] atmospheric variation where practical
```

---

## 53. Dialogue Checklist

Dialogue should have:

```text
[ ] character identity
[ ] portrait where appropriate
[ ] readable dialogue box
[ ] short natural lines
[ ] expressive presentation
[ ] clear continuation input
```

---

## 54. Implementation Decision Rule

Before adding any visual element, ask:

1. Does this look like an ordinary pixel-art RPG?
2. Does it support the story?
3. Does it improve gameplay clarity?
4. Does it match the project's visual reference?

If the answer is no to most of these:

> **Do not add it.**

## 56. Critical Agent Instruction

When implementing the game, **do not reinterpret the visual style**.

The intended result is:

> **A pixel-art narrative RPG set in an ordinary fictional city, with expressive characters, atmospheric environments, visual-novel dialogue, restrained retro UI, and cinematic glitch transitions.**

It is NOT:

> **A cyberpunk accessibility dashboard inside a futuristic handheld console.**

If the implementation begins to resemble the second description, the visual direction has been violated and the implementation should be corrected before adding more features.
