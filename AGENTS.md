# AGENTS.md

# Inclusive Interface --- Agent Instructions

## 1. Project Identity

**Project:** Inclusive Interface\
**Type:** Educational narrative game\
**Purpose:** Teach developers and designers about inclusive digital
design through gameplay.

The game is **not an accessibility tool for disabled users**. It is a
game for developers, designers, students, and digital product creators
that teaches accessibility through simulation, narrative, and design
decisions.

The central message is:

> **You didn't fail. The interface did.**

------------------------------------------------------------------------

# 2. Core Product Vision

Build a polished narrative RPG / visual-novel hybrid in which the
player:

1.  Starts as a young developer.
2.  Experiences an intentionally inaccessible website.
3.  Realizes that interface design can exclude users.
4.  Becomes a digital product designer.
5.  Explores a fictional city.
6.  Meets users with different accessibility needs.
7.  Understands their problems through natural dialogue.
8.  Makes accessibility-related design decisions.
9.  Sees the fictional interface change based on those decisions.
10. Earns score and progresses through Easy, Medium, and Hard
    difficulty.
11. Finishes with an accessibility evaluation.

The game should feel like a **real game first** and an educational
product second.

------------------------------------------------------------------------

# 3. Non-Negotiable Concept Rules

### Rule 1 --- Do not turn the game into a quiz website

The player should explore, interact, talk to characters, and discover
problems.

### Rule 2 --- Do not make characters lecture the player

Accessibility concepts should emerge through conversations and
situations.

### Rule 3 --- Do not portray disabled characters as helpless

Characters should have personalities, goals, jobs, opinions, humor, and
independence.

### Rule 4 --- The inaccessible interface is intentional

The simulated appointment website is supposed to contain accessibility
failures.

### Rule 5 --- The actual game must remain accessible

Do not copy the intentionally bad design into the actual game UI.

### Rule 6 --- Show consequences

Whenever possible:

> Player decision → Interface changes → User experience changes.

### Rule 7 --- Preserve the emotional opening

The sequence:

> **YOU DIDN'T FAIL.**

followed by:

> **BUT THE INTERFACE DID.**

is a core narrative moment and should not be removed.

------------------------------------------------------------------------

# 4. Visual Direction

Use a visual language inspired by:

-   Retro pixel-art RPGs
-   8-bit / 16-bit games
-   Handheld RPG interfaces
-   Pixel-art visual novels
-   Retro computer interfaces
-   RPG exploration games

The game can have a Roblox-like sense of exploration and environmental
discovery, but it should visually remain its own original game.

Do not copy existing game characters, logos, assets, UI, or copyrighted
artwork.

------------------------------------------------------------------------

# 5. Game Presentation

The game should combine:

-   Top-down or slightly angled RPG exploration
-   Pixel-art characters
-   Character portraits
-   Dialogue boxes
-   Environmental interactions
-   Cinematic transitions
-   Glitch effects
-   Interactive UI simulations
-   Multiple-choice decisions

The player should feel like they are moving through a world rather than
clicking through slides.

------------------------------------------------------------------------

# 6. Communication & Writing Rules

## 6.1 Dialogue must sound human

Prefer:

> **RAHUL:**\
> "I can find the button. I just don't know what it does."

Avoid:

> "Because I have a visual impairment, semantic labeling is necessary
> for accessibility."

The first sounds like a character.

The second sounds like a textbook.

------------------------------------------------------------------------

## 6.2 Keep dialogue concise

Most dialogue lines should be short.

Use pauses and reactions instead of long explanations.

Good:

> "Which button?"

> "The green one."

> "That doesn't help."

Bad:

> "People with color vision deficiencies may experience difficulty
> distinguishing certain colors, therefore the interface should provide
> additional indicators."

The educational explanation can appear after the decision as a short
feedback message.

------------------------------------------------------------------------

## 6.3 Characters need distinct personalities

Do not make every NPC sound identical.

Example:

**Rahul** - Calm - Observant - Slightly sarcastic

**Fatima** - Energetic - Confident - Humorous

Other characters should also receive distinct personalities.

------------------------------------------------------------------------

## 6.4 Avoid pity-based writing

Do not write characters as victims whose entire personality is their
disability.

The problem should generally be framed as:

> **Mismatch between the user and the interface.**

Not:

> **The user is incapable.**

------------------------------------------------------------------------

# 7. Narrative Structure

The opening sequence should follow this exact emotional progression:

``` text
BLACK SCREEN
    ↓
SYSTEM INITIALIZING
    ↓
USER PROFILE: UNKNOWN
    ↓
WHAT IF THE INTERFACE WASN'T DESIGNED FOR YOU?
    ↓
SIGN UP
    ↓
DEVELOPER'S ROOM
    ↓
GRANDMA REQUESTS DOCTOR APPOINTMENT
    ↓
INACCESSIBLE WEBSITE
    ↓
30-SECOND CHALLENGE
    ↓
PLAYER SUCCEEDS OR FAILS
    ↓
BLACK SCREEN
    ↓
YOU DIDN'T FAIL.
    ↓
BUT THE INTERFACE DID.
    ↓
DIGITAL PRODUCT DESIGNER
    ↓
CITY
```

Do not remove the opening challenge because it establishes the game's
purpose through experience.

------------------------------------------------------------------------

# 8. First Challenge Requirements

The simulated doctor's appointment website should contain deliberate
accessibility barriers.

Possible barriers:

-   Tiny text
-   Poor contrast
-   Poor information hierarchy
-   Tiny click targets
-   Confusing form labels
-   Poor CAPTCHA
-   Color-only status information
-   Distracting elements
-   Difficult navigation
-   Excessive cognitive load

The player gets approximately:

> **30 SECONDS**

The goal is to create understandable frustration, not unfair difficulty.

The player should be able to understand what they are trying to do.

------------------------------------------------------------------------

# 9. Main Game Loop

Every accessibility encounter should follow approximately:

``` text
EXPLORE
 ↓
FIND NPC
 ↓
TALK
 ↓
UNDERSTAND USER'S GOAL
 ↓
DISCOVER BARRIER
 ↓
DESIGN QUESTION
 ↓
CHOOSE SOLUTION
 ↓
FEEDBACK
 ↓
INTERFACE CHANGES
 ↓
SCORE
 ↓
CONTINUE EXPLORING
```

Do not replace the exploration and dialogue portions with a sequence of
disconnected quizzes.

------------------------------------------------------------------------

# 10. Accessibility Categories

The game should cover multiple types of accessibility.

At minimum:

### Visual

Examples: - Poor contrast - Tiny text - Missing labels - Poor
structure - Non-descriptive controls

### Hearing

Examples: - Audio-only instructions - Videos without captions -
Sound-only notifications

### Motor

Examples: - Tiny targets - Excessive precision - Difficult drag
interactions - Short time limits - Poor keyboard navigation

### Cognitive

Examples: - Confusing hierarchy - Complex instructions - Too many
choices - Unexpected navigation - Distracting animation

### Color Vision

Examples: - Color-only status - Red/green indicators without labels -
Charts relying only on color

### Language

Examples: - Complex terminology - Missing language options - Poor
translation - Unclear wording

------------------------------------------------------------------------

# 11. Character Design Rules

Characters representing accessibility needs must remain complete human
characters.

Each character should have:

-   Name
-   Personality
-   Goal
-   Background
-   Daily-life context
-   Individual speech style
-   Specific interface problem

Do not make the character's disability their only personality trait.

------------------------------------------------------------------------

# 12. Challenge Design Rules

Each challenge should test a real design principle.

A good challenge has:

``` text
USER NEED
    ↓
OBSERVABLE PROBLEM
    ↓
POSSIBLE SOLUTIONS
    ↓
ONE BEST SOLUTION
    ↓
VISIBLE INTERFACE CHANGE
    ↓
SHORT EXPLANATION
```

Avoid questions where the correct answer is arbitrary.

The player should be able to reason toward the correct answer from the
scenario.

------------------------------------------------------------------------

# 13. Multiple-Choice Rules

Use approximately 3--4 options.

Wrong answers should be plausible but address the wrong problem.

Example:

### Problem

A user cannot tell what controls do.

### Options

A. Add more animations\
B. Make everything brighter\
C. Add clear descriptive labels\
D. Add background music

Correct:

**C**

The game should explain why briefly after selection.

------------------------------------------------------------------------

# 14. Feedback Rules

## Correct

Prefer:

> **GOOD DESIGN.**

Then show the interface improving.

Example:

``` text
BEFORE

[ ? ] [ ? ] [ ? ]

AFTER

[ BOOK ] [ EDIT ] [ CANCEL ]
```

Then:

> "Clear labels make controls easier to understand."

------------------------------------------------------------------------

## Incorrect

Do not simply display:

> WRONG!!!

Prefer:

> **THAT DOESN'T SOLVE THE BARRIER.**

Then explain the issue in one or two short lines.

The game is educational.

The player should learn from mistakes.

------------------------------------------------------------------------

# 15. Scoring

Recommended scoring:

``` text
Correct decision          +100
First-attempt bonus        +25
Efficient solution         +10
Extra barrier identified   +25
```

Do not make the scoring system overly complicated for the MVP.

The important thing is to make progress visible.

------------------------------------------------------------------------

# 16. Accessibility Score

Maintain category-based progress.

Example:

``` text
VISUAL       █████████░ 90%
HEARING      ████████░░ 80%
MOTOR        ███████░░░ 70%
COGNITIVE    █████████░ 90%
LANGUAGE     ████████░░ 80%
```

The score represents the quality of the player's design decisions.

It should not imply that a real person's disability can be reduced to a
number.

------------------------------------------------------------------------

# 17. Difficulty Progression

## EASY

Focus on recognizing obvious barriers.

One main accessibility problem per challenge.

## MEDIUM

Multiple barriers appear together.

The player must determine the best intervention.

## HARD

The problem is communicated indirectly.

The player must infer the accessibility need from conversation and
observation.

Hard mode should test understanding rather than memorization.

------------------------------------------------------------------------

# 18. Interface Evolution

The player must be able to see their design decisions affecting the
simulated product.

For example:

### Before

-   Low contrast
-   Tiny controls
-   Missing labels
-   Color-only indicators

### After

-   Improved contrast
-   Larger interaction targets
-   Descriptive labels
-   Text/icon alternatives

Whenever practical, make the transformation visually obvious.

------------------------------------------------------------------------

# 19. Actual Game Accessibility

The game itself must not reproduce the accessibility failures being
simulated.

Implement or plan for:

-   Adjustable text size
-   Captions/subtitles
-   Text alternatives for important audio
-   Keyboard/controller support
-   Clear focus states
-   Non-color-only indicators
-   Readable contrast
-   Clear navigation
-   Reduced-motion option where practical
-   Adjustable timing where practical
-   Language support where practical

If a simulated inaccessible UI is implemented, isolate it from the main
game UI.

------------------------------------------------------------------------

# 20. UI/UX Rules

The real game UI should have:

-   Clear hierarchy
-   Consistent controls
-   Obvious interactive states
-   Readable text
-   Adequate click/touch targets
-   Consistent navigation
-   Clear feedback
-   Minimal unnecessary decoration

Retro aesthetics should never be an excuse for unusable controls.

------------------------------------------------------------------------

# 21. Glitch Effects

Glitches are part of the narrative language.

Use them for:

-   Major transitions
-   System messages
-   Emotional revelations
-   Level transitions
-   Important UI changes

Do not apply glitch effects constantly.

Important dialogue must remain readable.

------------------------------------------------------------------------

# 22. Audio

Audio should support the story rather than overwhelm it.

### Opening

-   Low ambient sound
-   Keyboard
-   Laptop hum
-   Subtle glitch effects

### 30-second challenge

-   Timer sound
-   Light tension
-   Error feedback

### City

-   Calm background music
-   Environmental ambience
-   Footsteps

### Major realization

Reduce or remove music temporarily.

Silence can be more effective than dramatic music.

------------------------------------------------------------------------

# 24. Anti-Gravity Implementation Behavior

When working on this project, the coding agent should:

1.  Read `GAME_DESIGN.md` before implementing major features.
2.  Preserve the game's narrative tone.
3.  Avoid changing the core concept without explicit instruction.
4.  Prefer modular systems.
5.  Keep scenes/components reusable.
6.  Keep game data separate from rendering logic where practical.
7.  Avoid hardcoding every dialogue line directly into UI components
    when a dialogue data structure can be used.
8.  Avoid creating unnecessary dependencies.
9.  Keep the MVP runnable.
10. Test changes after implementation.
11. Do not replace game mechanics with static mockups unless explicitly
    requested.
12. Do not remove accessibility simulation mechanics.
13. Do not make the actual game UI intentionally inaccessible.
14. Preserve existing working features when adding new ones.

------------------------------------------------------------------------

# 26. Data-Driven Content

Where practical, keep:

-   Character information
-   Dialogue
-   Questions
-   Answers
-   Accessibility categories
-   Score values
-   Interface transformations

in data files rather than scattering them throughout application code.

This makes it easier to add new scenarios.

------------------------------------------------------------------------

# 27. Dialogue Implementation

Dialogue should support at least:

-   Character name
-   Dialogue text
-   Character portrait
-   Expression
-   Speaker
-   Optional sound effect
-   Optional scene effect
-   Next dialogue entry
-   Branching choice where needed

Example conceptual data:

``` text
speaker: Rahul
expression: neutral
text: "I can find the button. I just don't know what it does."
next: rahul_question_01
```

Do not hardcode a large branching story into one giant function.

------------------------------------------------------------------------

# 28. State Management

The game should track at minimum:

``` text
player name
current scene
current level
score
accessibility category scores
completed challenges
chosen answers
unlocked locations
```

If the technology supports it, keep these in a centralized game state.

------------------------------------------------------------------------

# 29. Error Handling

Errors should fail gracefully.

For example:

-   Missing dialogue → show fallback text or log a clear error
-   Missing asset → use a safe placeholder
-   Invalid question data → prevent the game from crashing
-   Missing scene → show a clear development error

Never silently break the entire game because one asset or dialogue entry
is missing.

------------------------------------------------------------------------

# 30. Performance

For the hackathon MVP:

-   Avoid unnecessary heavy dependencies.
-   Optimize large images/assets where practical.
-   Avoid expensive continuous effects unless necessary.
-   Keep animations lightweight.
-   Prefer simple pixel-art assets.
-   Do not sacrifice stability for visual effects.

A polished stable demo is more valuable than an enormous unstable game.

------------------------------------------------------------------------

# 31. Asset Rules

Use:

-   Original assets
-   Properly licensed assets
-   Open-source assets with compatible licenses
-   Procedurally generated assets where appropriate

Do not directly copy assets from:

-   Pokémon
-   Persona
-   Roblox
-   Nintendo games
-   Existing Pinterest artwork
-   Other copyrighted games

Reference images are for **visual direction**, not direct asset
extraction.

------------------------------------------------------------------------

# 32. Content Rules

The game should:

-   Respect people with disabilities.
-   Avoid stereotypes.
-   Avoid pity narratives.
-   Avoid treating accessibility as charity.
-   Focus on inclusive design.
-   Use respectful language.
-   Show people as independent users.

The central conflict should be:

> **Bad design creates barriers.**

------------------------------------------------------------------------

# 33. What the Agent Should Not Do

Do not:

-   Turn the project into an accessibility website.
-   Replace the RPG concept with a standard dashboard.
-   Remove the opening 30-second challenge.
-   Remove the city exploration concept.
-   Turn every interaction into a multiple-choice quiz.
-   Make NPCs deliver textbook explanations.
-   Use disability stereotypes.
-   Make the actual game inaccessible.
-   Copy existing game's art or characters.
-   Over-engineer the MVP.
-   Add unrelated features simply because they are technically
    interesting.

------------------------------------------------------------------------

# 34. Design Decision Priority

When two implementation choices conflict, prioritize in this order:

``` text
1. Core player experience
2. Narrative clarity
3. Accessibility
4. Gameplay functionality
5. Visual consistency
6. Performance
7. Technical elegance
```

Do not sacrifice the core experience for unnecessary technical
complexity.

------------------------------------------------------------------------

# 36. Definition of Done

A feature is considered complete when:

-   It works in the game.
-   It matches the game design.
-   It has clear player feedback.
-   It does not break existing gameplay.
-   It follows the project's accessibility principles.
-   It has no obvious console/runtime errors.
-   It can be demonstrated reliably.

For major features, test the complete player flow rather than only the
individual component.

------------------------------------------------------------------------

# 37. Final Guiding Principle

Whenever implementing or designing a feature, ask:

> **Does this help the player understand what it feels like when an
> interface isn't designed for them?**

If yes, it belongs in the experience.

If it does not contribute to the game's core message, gameplay,
narrative, accessibility education, or hackathon demo, avoid adding it
unless explicitly requested.

------------------------------------------------------------------------

## Final Project Principle

> **Don't teach accessibility by telling players what to think.**
>
> **Make them experience the problem.**
>
> **Then let them solve it.**
